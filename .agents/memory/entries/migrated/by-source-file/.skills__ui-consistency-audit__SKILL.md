# UI Consistency Audit

Find and prove **systemic** UI inconsistencies in DB Pro's native egui UI: the same
component behaving differently across call sites, controls that do not share a row
rhythm, menus that are unreachable, states that are missing, and labels/strings that
bypass the shared contracts.

Two rules separate this skill from a visual opinion:

1. **Every finding has a runtime measurement or a component-contract citation** —
   `file:line` plus, where layout is claimed, a WID/geometry number from the capture
   harness.
2. **The component is guilty until proven innocent.** When two call sites disagree,
   read the shared component first; the wrapper/layout/default inside the component is
   usually the root cause, not the view.

## Quick start

```bash
# 1. Inventory every Select call site and component-contract violation
python3 .skills/ui-consistency-audit/scripts/ui_consistency_scan.py

# 2. Capture the affected surfaces (needs a display; Xvfb is fine)
bash .skills/ui-consistency-audit/scripts/capture_ui_matrix.sh --surface query --audit

# 3. Read the persistent memory BEFORE reporting anything
#    .skills/ui-consistency-audit/references/findings-ledger.md
#    .skills/ui-consistency-audit/references/heuristics.md
```

## Workflow

### 1. Frame the question

Turn the request into a measurable claim, e.g. "the schema select, row-limit select,
and sidebar filter do not share a vertical rhythm". Write the claim down; an audit
without a falsifiable claim degenerates into taste.

### 2. Static pass — inventory

Run the scanner. Then, for each call site of the component under audit:

- Open the shared component (`crates/ui/src/components/<name>/`).
- List the props it accepts and the **defaults** it applies (`theme`, size, width,
  label, enabled, error, keyboard behavior).
- Note which props are optional and what happens when the caller omits them. Optional
  props with visual consequences are where inconsistencies breed.

Full procedure: `references/method.md`.

### 3. Runtime pass — measure

Capture the surface through the app's own harness, never a mock:

```bash
DB_PRO_CAPTURE_TO=/tmp/ui-audit/query.png \
DB_PRO_WINDOW_SIZE=1440x900 \
DB_PRO_CAPTURE_QUERY=1 \
DB_PRO_AUDIT_JSON=/tmp/ui-audit/query.json \
DB_PRO_INSPECTOR_DUMP=1 \
./target/debug/db-pro-native
```

- `DB_PRO_AUDIT_JSON` is **mandatory** for the inspector dump; without it
  `DB_PRO_INSPECTOR_DUMP` prints nothing.
- Compare geometry in the JSON/WID log: `y` ranges of sibling controls in the same
  row, `x` ranges inside right-to-left areas, heights vs token values.
- A claim without a number is a hypothesis, not a finding.

Runtime quirks that have already cost time:

- The app prefers Wayland if `WAYLAND_DISPLAY` is inherited. Force X11
  (`WINIT_UNIX_BACKEND=x11 DISPLAY=:0`) or run under `xvfb-run`.
- The capture engine writes a PNG only when the surface actually opened; a missing
  file means the fixture did not open, not that the UI is fine.
- Select stores open state in egui temp data. `egui::Popup::open_id` does **not**
  open it; use the harness hook for the specific select (see `capture.rs`).

### 4. Classify

Use `references/heuristics.md` for the current anti-pattern catalog. Severity follows
`AGENTS.md`: P1 = a user flow is broken or the wrong control is hit; P2 = visual
inconsistency, missing state, or a11y gap that does not block the flow.

False positives are recorded, not deleted: a hidden focus anchor or a deliberate
compact density is not a defect.

### 5. Fix with evidence

- Fix the shared component before patching call sites.
- Add a unit test for the pure geometry/layout decision (the repo keeps tests in
  `tests/<stem>_tests.rs`).
- Re-run the same capture and compare the same numbers. "Looks better" is not
  evidence.

### 6. Self-improve (mandatory close-out)

After every audit or fix round, update the skill's memory:

| File | Update |
|---|---|
| `references/findings-ledger.md` | Add new findings with stable IDs, evidence, status (`open` / `fixed <sha>` / `false-positive` / `deferred`). Never reuse an ID. |
| `references/heuristics.md` | If the finding generalizes, add it as a named rule with the tell-tale code pattern. |
| `scripts/ui_consistency_scan.py` | If the pattern is statically detectable, add a scanner rule (and a fixture test). A heuristic that cannot be detected statically stays in the ledger as prose. |

The loop is: **audit → record → generalize → detect next time**. A round that does not
update at least one of these files did not self-improve.

## Report format

Use tables, no prose-only dumps. Each finding row:

```text
ID | Severity | Component/surface | file:line | Runtime evidence | Status
```

Follow with: measured geometry, root cause, false positives rejected, evidence gaps
(what could not be captured), and a fix order. End implementation handoffs with a
short Vietnamese summary per `AGENTS.md`.
