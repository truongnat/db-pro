# Agents — feature research and recommendation

- Research date: 2026-09-24
- Repository baseline: `b0500b9a7ecbe37b454f3d917881154c5f7a403c`
- Scope: native Agent workflow, trust and context boundary, tool authorization, AI egress, provider setup, competing workflow patterns, and Phase H/capability-matrix drift. No implementation is included.

## Decision

**Keep the existing right-side Agent surface and typed-service architecture; do not treat it as a blank-slate chat feature or as completion of Phase H.** Source already implements eleven typed tools, a multi-step orchestrator, document-specific sessions, bounded context/results, explicit patch and SQL confirmations, runtime key lifecycle, and canonical schema/query/monitoring service reuse (`agents-baseline.md`). Agent Workflow remains `RUNTIME_VERIFY`; corrected status says live-provider and native UI PASS claims lack retrievable runtime artifacts (`docs/plans/STATUS.md:45`; `docs/plans/active/agent-workflow/VERIFICATION.md:3`).

**Before expanding the tool surface, align four P2 boundaries:** fix or clarify ExplainQuery’s mode contract; make data-egress disclosure and endpoint configuration describe the actual payload/destination; decide whether trusted workspace files are intended context or remove the misleading file-context gate; reconcile Phase H and capability documentation to source. These are source-derived behavior/documentation inconsistencies, not reproduced incidents. No P0/P1 was established in this research.


## Recommended product workflow

1. **Choose scope before sending.** Keep the query document, connection/schema and selection as the explicit current scope. Show the exact context sent (prompt, SQL, schema/table metadata, diagnostics, and any result samples) and make any workspace-file attachment individually visible. Provide a direct per-run or per-connection way to omit sensitive context; “workspace trusted” alone is not a clear consent boundary for database/query data.
2. **Separate answer, edit and execute.** Ask is explanatory/read-only, Edit proposes a diff and applies only after review, Agent may run SQL. Keep `Ask` as the safe default. Publish the same exact tool permissions to the provider and enforce them again in workflow + executor. Resolve ExplainQuery’s current Ask/Edit allowlist-versus-execution-policy conflict rather than silently relying on fallback errors.
3. **Make every tool observable.** Preserve the current bounded tool activity, stable call IDs, explicit pending confirmation, and run/result correlation. Bind confirmation to the actual SQL, target connection and document version; do not add DDL execution paths that bypass confirmation, session termination, or autonomous multi-step mutation.
4. **Treat provider identity as configuration, not a display label.** Current UI supports Groq/OpenAI key-prefix selection, but endpoint/model environment overrides are also accepted. Expose the actual provider/endpoint class and its active scope; never imply that an OpenAI/Groq key prefix alone proves which host receives the key.
5. **Grow capabilities only over canonical services.** Existing `MonitoringRead` and `SuggestIndexes` are narrow baseline tools. Add richer routine/compare/performance/sample-data workflows only when the corresponding typed services, caps, provider boundaries, confirmations and runtime evidence exist. Keep the native panel, task-level prompts and selection affordances rather than widening to general file/system automation.

## Reference workflow comparison

Official DBeaver AI Assistant documentation describes chat, query suggestion, SQL explanation, error troubleshooting and object descriptions; it also lists AI tools, custom prompts, and file/data-transfer assistance: [AI Assistant](https://dbeaver.com/docs/dbeaver/AI-Smart-Assistance/).

Its [AI settings](https://dbeaver.com/docs/dbeaver/AI-Assistance-settings/) support multiple provider/model profiles, defaults, per-class query execution settings, metadata inclusion controls, and sample-row limits. The [data-privacy guide](https://dbeaver.com/docs/dbeaver/AI-Assistance-and-Data-Privacy/) says schema table/column names go to the provider, requires first-use consent for metadata transmission per connection, allows scoping excluded tables, and identifies provider-specific privacy policies. These are comparison points, not a directive to copy DBeaver’s larger feature surface or its default execution settings.

## Prioritized open work

1. **P2 — Align ExplainQuery mode authorization.** `is_tool_allowed` lists ExplainQuery for Ask and Edit, but `AgentWorkflow::request_tool` then passes it through `execution_decision`, which rejects every non-Agent mode. Executor repeats the Agent-only guard. Thus an ExplainQuery provider call authorized by the mode allowlist fails in Ask/Edit (`crates/core/src/domain/agent_workflow.rs:541-570,367-382`; `core/src/domain/agent.rs:398-410`; `crates/runtime/src/agent_executor.rs:451-473`). Decide whether safe EXPLAIN belongs in Ask/Edit; make both decision layers match. Also publish only the tool definitions allowed in the active mode, or make rejection/fallback behavior intentional and visible (`runtime/src/agent.rs:197-210,572-595`). This is a feature-contract defect, not a mutation bypass: query execution and confirmation guards remain active.
2. **P2 — Make provider disclosure match serialized Agent context and destination.** The settings note names prompts, referenced SQL, schema names/types and sample rows (`crates/ui/src/agent_settings_view.rs:7-8,65-79`). Actual core `AgentContext` additionally serializes document ID/version, connection ID, selected range and diagnostic messages (`crates/core/src/domain/agent_context.rs:112-125,212-225`; `crates/runtime/src/agent.rs:379-414`). In addition, `DB_PRO_GROQ_ENDPOINT` and `DB_PRO_CODEX_ENDPOINT` can select a custom HTTPS endpoint and the configured key is sent as Bearer auth (`runtime/src/agent.rs:134-152,163-183,237-245`). Release egress documentation that names only the two defaults should explicitly account for these overrides (`docs/release/known-limitations.md:303-315`). Avoid privacy/retention claims based only on `store: false`; that request field does not establish provider retention policy.
3. **P2 — Resolve workspace trust/context mismatch.** Submit blocks when workspace files are attached but the IDE workspace is untrusted, with the message “Trust the workspace before sending folder/file context to Agent” (`crates/ui/src/agent_actions.rs:67-73`). The typed run builder sends the core query/schema context and not the UI `workspace_context_items` (`agent_actions.rs:143-179`; `core/domain/agent_context.rs:112-125`). The source does not show file contents crossing to the provider in this workflow. Either implement bounded, visible file-context inclusion after trust, or remove the dead gate/message; do not represent a trust check as evidence of file transmission.
4. **P2 — Refresh Phase H and capability/evidence records.** H-AI goal says nine tools and says monitoring/index suggestions are missing; current source has eleven tools, `MonitoringRead`, and `SuggestIndexes` (`docs/goals/goal-phase-h-ai.md:22-65`; `core/domain/agent.rs:220-235`; `runtime/src/agent.rs:572-627`). Capability matrix §7 similarly says index suggestion and sessions/locks inspection are missing (`docs/notes/PRODUCT_CAPABILITY_MATRIX.md:213-233`), even though the existing monitoring tool returns counts and a small active-query sample—not full session/lock inspection (`runtime/src/agent_executor.rs:287-321`). Also preserve `RUNTIME_VERIFY`: the corrected Status entry rejects unretrievable live-provider/UI pass claims while the workflow verification later lists required scenarios as PASS (`docs/plans/STATUS.md:45`; `active/agent-workflow/VERIFICATION.md:3,32-69`). Refresh actual scope and provider-specific evidence without upgrading lifecycle status.

## Recommendation boundary

The current security shape is strong enough to retain: typed tools, central services, bounded serialization, no direct credential tool, duplicate-call protection, and a confirmation gate before mutating/destructive execution. Treat the four P2s as consistency and trust-work improvements before adding broader context or tool power. Then scope Phase H against the authoritative full-product goal, not stale matrix counts. PostgreSQL and SQLite support and runtime verification must stay separate; source-level shared paths do not prove either provider.

## Research limits

Only code/docs and official DBeaver documentation were inspected. No test, build, live provider request, PostgreSQL/SQLite interaction, mutation, or native UI walkthrough was run. The P2s describe source-level contract mismatches; they were not reproduced in a running app. No change to feature lifecycle, plan status, provider support, or product code is proposed by this research.
