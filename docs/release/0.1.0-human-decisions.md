## HD-001 — License — DECIDED

| Field | Value |
|---|---|
| ID | `HD-001` |
| Decision | Which license (if any) the project and the v0.1.0 artifacts are released under, and whether a `LICENSE` file plus manifest metadata are added. |
| Options | (a) a permissive license (e.g. MIT or Apache-2.0) for the code; (b) a copyleft license (e.g. GPL-3.0/AGPL-3.0); (c) no open-source license — keep all rights reserved and distribute only under a custom/internal agreement; (d) defer the decision entirely and do not publish any artifact publicly. |

## HD-002 — Accept unsigned distribution

| Field | Value |
|---|---|
| ID | `HD-002` |
| Decision | Whether to accept shipping **unsigned** artifacts for a public release, or to block public release until platform signing/notarization is configured. |
| Options | (a) accept unsigned and state the OS warnings in the release notes (current recorded status for the *internal* RC); (b) block public release until macOS Developer ID + notarization and Windows code signing exist; (c) sign without notarization (partial — macOS still warns and Gatekeeper may still block). |
| Impact | User trust and first-run friction: macOS shows *"…cannot be opened because the developer cannot be verified"* (right-click → Open / Privacy & Security → Open Anyway); Windows SmartScreen shows *"Windows protected your PC"*; Linux artifacts are simply unsigned. Measured state: `Signature=adhoc`, `flags=0x20002(adhoc,linker-signed)`, `TeamIdentifier=not set`, `spctl -a -vvv -t execute` **rejects** (risk register `R003`; `docs/release/evidence/v01-06/03-release-binary.txt`). No certificates exist and no signing secrets were added. Note the interaction with `R-KEYRING-STALL`: ad-hoc signing is what makes the Keychain read require an interactive grant (`providers/22`). |
| Recommended default | For the **internal RC**: accept as already recorded (`R003` `ACCEPTED`). For **public**: owner decision; if signed distribution is later wanted, it is a new build with a new candidate SHA and a new CI run — the current ad-hoc-signed archives will not become signed. |

## HD-003 — Windows/Linux runtime requirement

| Field | Value |
|---|---|
| ID | `HD-003` |
| Decision | What runtime evidence the Windows and Linux artifacts require before they are published, given that no Windows or Linux host exists in this project. |
| Options | (a) publish all three archives with the limitation disclosed (`BUILD_VERIFIED` / `PACKAGE_VERIFIED`, never `RUNTIME_VERIFIED`); (b) hold the Windows/Linux archives back from the public download set until at least a launch smoke has been recorded on each platform; (c) narrow the public contract to macOS ARM64 only for 0.1.0. |
| Impact | Directly controls what cross-platform claims may be made. Both platforms **compile and package green in CI** (final run `34860902181`, values in `0.1.0-handoff.md` §3) and no process has ever been launched from either archive. Linux additionally needs a D-Bus Secret Service provider for credential storage (`B-7`). Publishing (a) without disclosure would overstate quality; (b) delays the release and needs hardware/VMs; (c) shrinks the audience. Register entry: `R-WINLINUX` (`OPEN`; `ACCEPTED` for the internal macOS-ARM64 RC, `BLOCKING` for cross-platform *runtime* claims). |
| Recommended default | Do not make runtime-quality claims for either platform. Either publish the archives with the `BUILD_VERIFIED`/`RUNTIME_UNVERIFIED` limitation stated verbatim, or omit them from the public download set — the owner picks which; what must not happen is a silent third option where the archives ship without the limitation stated. |
| Owner choice | **PENDING** |

## HD-006 — `F1` `pg_restore` version-skew disposition

| Field | Value |
|---|---|
| ID | `HD-006` |
| Decision | What to do about finding `F1`: under PostgreSQL **client 18.4 / server 16.15** skew, a custom-format restore completes but `pg_restore` exits 1 (`SET transaction_timeout = 0`, a PG17+ GUC), and the app reports `restore failed` on any nonzero exit (`crates/infrastructure/src/backup/pg_dump.rs:167-170`). |
| Options | (a) **docs-only**: state the client/server version expectation in `docs/release/platform-prerequisites.md` and keep the nonzero-exit check exactly as it is; (b) **code change**: detect the version pair before a custom-format restore (needs a new candidate SHA, a new CI run and the six gates re-run, because it touches the backup path); (c) weaken the exit-code check to tolerate this specific error — **explicitly not recommended and not done**: failing on a nonzero `pg_restore` exit is the safe default and relaxing it risks silently accepting a partial restore. |
| Impact | A user can be told "restore failed" when the restore in fact completed. No data is lost and nothing is written to the wrong target, so `F1` is `P2`, not `P1` (`providers/23`). Option (b) is production work in the credential/backup path and invalidates the current artifact candidate; option (a) is a one-file docs edit. |
| Recommended default | (a) for 0.1.0 — document the version expectation and keep the safe behaviour — with (b) scheduled after 0.1.0. Recorded but not executed by this pass. |
| Owner choice | **PENDING** |

## HD-007 — Interactive GUI smoke gate

| Field | Value |
|---|---|
| ID | `HD-007` |
| Decision | What interactive (GUI) evidence must exist before a **public** release, given that no window has ever been rendered or interacted with on a packaged build (`R-GUI-SMOKE`, `OPEN`; all 165 manual-smoke items blocked in this environment). |
| Options | (a) require the full `docs/release/0.1.0-interactive-verification-runbook.md` (~30–60 minutes: launch/render, Settings, SQLite connection, query, table edit with apply, read-only safety attempt, destructive confirmation, schema introspection, ER pan/zoom/search, export, ⌘Q quit, relaunch persistence) and file the results + named screenshots; (b) require a **reduced** minimum (launch + window renders + one query executes) as the gate; (c) release publicly with no interactive evidence, accepting the risk explicitly and disclosing it. |
| Impact | It is the difference between a build that is *verified to launch* and one that is *verified to be usable*. | Recommended default | (a) — the full runbook; it is a single sitting and converts every `PENDING_HUMAN` item into evidence. If the owner prefers (b), the reduced gate must be written down and the remaining items must stay `blocked`/`not-run` rather than silently dropped. |

## What happens after the owner decides

Each decision, when made, must be recorded in `docs/release/risk-register.md` (§3 decision
records, `DECISION D…`) with the date and rationale, and the affected documents updated in the
same pass: `0.1.0-readiness.md` (`READY_FOR_RELEASE` / §45 decisions), `0.1.0-handoff.md`,
`0.1.0-release-checklist.md`, `known-limitations.md`, `0.1.0-release-notes.md`. A `YES` for
`PUBLIC_RELEASE_READY` requires all of: no P0, no open release-blocking P1, license decided, exact
artifacts built, the required host runtime smoke completed, and explicit risk dispositions —
`HD-007` is the owner decision that currently cannot be satisfied by any automated run.
