# DB Pro 0.1.0 — Interactive verification runbook (brief §47)

**What this is.** The executable, human-owned procedure that closes the interactive GUI gap. Every
GUI-dependent item in the release record is currently `PENDING_HUMAN` / `NOT VERIFIED` because this
repository's automation environment has **no window-server access** (Orca helper
`runtime_unavailable`; AppleScript `-1743` TCC denial; `screencapture` "could not create image from
display"; no accessibility tree — re-verified live 2026-09-14,
`docs/release/evidence/v01-runtime/providers/21-gui-unavailability-probes.txt`). **Running this
runbook is what converts those items into evidence.**

**Time:** **~30–60 minutes total** — about 10 minutes of terminal setup (Phase 0) and 20–50
minutes of interaction. 18 steps in 5 phases, ordered
so the two data-source setups (PostgreSQL container, SQLite fixture) are each touched once and the
app is launched twice (once for the session, once to check persistence).

**Rules.**
- Record what you actually observe. A step that does not behave as expected is a **finding**, not a
  failure to hide: note it, capture it, keep going. Do not tick anything you did not see.
- Expected observations below are **code-derived expectations** from
  `docs/release/0.1.0-ui-visual-description.md` (labels read out of `crates/ui/src/**`), not prior
  observations — treat a mismatch as information.
- Screenshots: save into `docs/release/evidence/v01-runtime/screenshots/` (the directory that
  already exists for exactly this purpose) using **exactly** the filenames below. The file numbers
  come from the delivery brief's capture set and are **not** step numbers.
- Results: write `docs/release/evidence/v01-runtime/human-session/README.md` with the SHA you
  tested, the date, the display resolution, and per-step observed/expected/deviations. Then tick the
  corresponding items in `docs/release/0.1.0-manual-smoke.md` (change `- [~]` to `- [x]` **only**
  for what you observed) and update `docs/release/evidence/v01-runtime/README.md`,
  `docs/release/0.1.0-handoff.md` §5 and `docs/release/0.1.0-readiness.md` (the GUI rows).
- If a Keychain authorization prompt appears before the window (known issue `R-KEYRING-STALL` /
  LIM-018), answer it (Allow) and note that it appeared. If it hangs instead, that is the stall
  reproducing — record it (it needs a stored `com.dbpro.app` item; see `providers/22`).

## Phase 2 — PostgreSQL, once (~6 min)

### Step 4 — Create the PostgreSQL connection

Click `+`/`New Connection` in the Explorer (tooltip `New Connection`). In the `New Connection`
dialog pick **PostgreSQL** (MySQL, MariaDB, Redis, MongoDB, ClickHouse and DuckDB show a disabled
`Soon` badge — click one and confirm it is disabled). Fill: display name (any), database
`dbpro_fixture`, host `127.0.0.1`, port `55432`, username `dbpro`, the password from step 0.3.
Leave SSL/SSH-tunnel off.

Click `Test Connection`. **Expected:** a success alert `Connection Verified` reading "Database
server is reachable and validated." Then `Save Connection`.

**Also test the negative path now** (30 seconds): edit the password to a wrong value, click `Test
Connection`, confirm a useful `Configuration Error` and **no crash**; then restore the password and
re-test (editing a field after a test must show "Connection changed · test again before saving").

**Record:** written observations.

### Step 5 — Explorer against PostgreSQL

In the Explorer, expand the new PostgreSQL connection → the `public` schema → tables/views. Click a
table once (expect a **Data preview** tab) and double-click it (expect a **permanent Data tab**);
confirm repeated clicks do not duplicate the same resource tab.

**Expected:** schemas expand/collapse; tables and the views list under the schema; the connection
node shows a connected state and the status bar reads `Connected` with the connection name, driver
and database.

**Capture:** `02-explorer-pg.png` — Explorer tree expanded to PostgreSQL tables, with the
connection visible.

### Step 6 — One PostgreSQL query, and the missing Stop button

Open a new query tab (`⌘N` or the `New query` button). Run:

```sql
SELECT * FROM orders;
```

**Expected:** a result grid with **4 rows**; the status bar shows a `N ms` duration; the right-hand
context label reads `SQL Editor`.

**Then confirm the capability gate by observation:** while the query is executing (use
`SELECT pg_sleep(3);` to make it visible) confirm the UI does **not** offer a Stop/cancel control
for PostgreSQL — cancellation is `Unsupported` for this provider by design
(`crates/core/src/domain/capabilities.rs:132`; verified correct in `providers/15`). Pressing
`Escape` must **not** claim to cancel.

**Record:** written observations.

## Phase 3 — SQLite interactive session (~20 min)

### Step 7 — Create the SQLite connection pointing at the fixture

`New Connection` → **SQLite**. Use `Browse File…` to open the native file picker and select
`/tmp/dbpro-human-verify/scratch.db` (also type the path directly once to confirm both work).
Click `Test Connection` → `Connection Verified`; then `Save Connection`.

**Expected:** an info card noting SQLite is embedded in-process; the file picker opens and
populates the path field; cancelling `Browse` leaves the field unchanged; the connection appears as
a root node in the Explorer.

**Record:** written observations.

### Step 8 — Query completion popup

Open a query tab on the SQLite connection and type (do not run yet):

```sql
SELECT * FROM us
```

**Expected:** a schema-aware completion popup offers `users` (tables/columns/keywords are offered
as you type). Then type `ers;` to complete the statement.

**Capture:** `03-query-completion.png` — the editor with the completion popup visible.

### Step 9 — Run queries and read the grid

Run `SELECT 1;` — expect a single row/column with value `1` and a duration in the status bar. Then
run:

```sql
SELECT * FROM users;
```

**Expected:** **60 rows**. Exercise the grid: page through (the fixture is sized for
pagination), apply a filter on `status` (e.g. `active`), sort by `created_at`, and confirm changing
the page clears page-local row selection. Confirm filtering/sorting really changes the returned
subset/order.

**Capture:** `04-query-results.png` — the result grid showing the `SELECT * FROM users;` result
(preferably with the row count / pagination visible).

### Step 10 — Table data edit / insert / delete with apply

Open the `users` table's Data tab. Edit a cell (e.g. change `full_name` of `id = 1`), stage a second
edit in the same row, then **Insert row** (choose a new `id`, unique `email`, a name and a status),
then **delete** one of the rows you just inserted — all **staged** first: confirm the change bar /
pending-changes badge reflects the staged set without duplicate full-row snapshots, then **Apply**
and **reload**.

**Expected after apply:** edits and the inserted row persisted in the database; the deleted row is
gone; the pending badge clears; no error. Verify from the terminal too:

```bash
sqlite3 /tmp/dbpro-human-verify/scratch.db "SELECT id, email, full_name, status FROM users WHERE id = 1;"
```

**Capture:** `05-table-edit.png` — the Data tab with the pending-changes bar and staged edits
visible (before Apply).

### Step 11 — 3-way conflict (Original / Local / DB Current)

Stage an edit in the grid (e.g. `full_name` of `id = 2` → `Local Edit`) but **do not apply**. In a
terminal, change the same row underneath the app:

```bash
sqlite3 /tmp/dbpro-human-verify/scratch.db "UPDATE users SET full_name = 'External Edit' WHERE id = 2;"
```

Now **Apply** in the app.

**Expected:** a 3-way conflict dialog appears showing Original / Local / Database Current for that
row, with `Keep Mine` and `Use Database` actions. Choose one and confirm the outcome matches the
action chosen (verify with the `sqlite3` query above). Record which action you used.

**Capture:** `06-conflict.png` — the conflict dialog with all three values visible.

### Step 12 — Read-only safety attempt

Create a second SQLite connection to the **same** scratch file with the `Read-only mode` checkbox
ticked (`Safety Policy` block). On that connection, attempt a write from the query editor:

```sql
UPDATE users SET status = 'suspended' WHERE id = 1;
```

**Expected:** the write is **blocked at the backend boundary** with a clear read-only error — not
silently ignored, not applied, no crash. Confirm with a terminal read that the row is unchanged.

**Record:** written observations. **This is a safety-boundary item — if the write succeeds, stop
and record it as a P0-class finding.**

### Step 13 — Destructive confirmation on a throwaway table

On the read-write SQLite connection, create a table you can afford to lose:

```sql
CREATE TABLE IF NOT EXISTS throwaway (id INTEGER PRIMARY KEY, note TEXT);
INSERT INTO throwaway (id, note) VALUES (1, 'delete me'), (2, 'and me');
```

Run the destructive statement **without a safe predicate**:

```sql
DELETE FROM throwaway;
```

**Expected:** a destructive-confirmation prompt appears **before** anything reaches the backend.
**Reject** it first → nothing deleted (verify with `SELECT count(*) FROM throwaway;` = 2). Then run
it again and **confirm** → the rows are deleted and the grid reflects it. Also try
`DROP TABLE throwaway;` and note the behaviour.

**Record:** written observations.

### Step 14 — Schema introspection (Columns / Indexes / Relations / Triggers / DDL)

Open the `users` table's workbench / structure surface and walk the sections: `Columns`, `Indexes`,
`Relations` (foreign keys), `Triggers`, `DDL`. Then open `user_roles` (composite primary key on
`(user_id, role)`) and confirm the composite key and its FK are shown, and `order_items` for its
triggers and composite unique index.

**Expected (per section):** columns with types/nullability/defaults; indexes including the unique
`idx_users_email` and the composite `idx_orders_status_total_cents`; relations showing
`orders.user_id → users.id` etc.; triggers `trg_order_items_after_insert` /
`trg_order_items_after_delete`; a reconstructed `CREATE TABLE` DDL that matches the fixture's
schema (compare against `fixtures/smoke/sqlite/runtime_fixture.sql`). Empty tables show a real
empty state. The header `Refresh` refreshes the current section.

**Capture:** `07-schema-columns.png` (Columns section) and `08-schema-indexes.png` (Indexes
section).

### Step 15 — ER diagram: pan, zoom, LOD, search

Right-click the SQLite connection's schema in the Explorer → `Open ER Diagram`. A new tab titled
`ER: <schema>` opens with `Diagram` and `Overview` section tabs.

- Pan by dragging; zoom continuously out to <0.75× (Compact LOD) and in past 1.15× (Detailed LOD).
- Use the search box to filter to one table; then expand the neighbourhood (BFS, depth 1–2).
- Click a column in the diagram → expect navigation to that table.
- Switch to `Overview` (expect the "coming soon" placeholder) and back — the diagram state must be
  preserved.

**Expected:** diagram renders the schema's tables (only that schema's), edges between related
tables, LOD transitions visibly change detail level, pan/zoom feel smooth on this 4-table schema
(note: the *large-schema* smoothness claim needs ≥200 tables and is a separate measurement — see
Step 15b). Idle CPU/memory: watch Activity Monitor while panning for ~30 s and note whether it
stays flat; do not claim a number you did not measure.

**Capture:** `09-er-compact.png` (zoomed out, Compact LOD) and `10-er-detailed.png` (zoomed in,
Detailed LOD).

**Step 15b (optional, for V01-03):** repeat pan/zoom on a large schema — the 200+ table fixture is
not in this repo; if you have one (Chinook/Sakila-scale SQLite or any 200+ table database), attach
it and record frame feel + Activity Monitor CPU/memory while panning. Otherwise record V01-03's
"smooth pan/zoom / idle CPU<2%" claim as **still unmeasured**.

### Step 16 — Agent panel (Preview)

Open the Agent panel (right-hand side / `Agent` rail icon). Confirm the `Preview` badge is
displayed, that the panel is clearly marked Preview, and that MCP is not presented as a working
0.1.0 feature. If a provider key was exported in step 0.4, run one prompt (e.g. "list the tables in

**Expected:** panel renders with Preview labelling; without a key it stays inert/offline with no
fake success message.

**Capture:** `11-agent.png` — the Agent panel with the Preview badge visible.

### Step 17 — Export

Run a small query (e.g. `SELECT id, email, status FROM users LIMIT 5;`), then use the `Export`
button in the result area (or the export entry in the toolbar overflow) to export CSV/TSV. Save to
`/tmp/dbpro-human-verify/` and verify from the terminal:

```bash
ls -l /tmp/dbpro-human-verify/*.csv && head -3 /tmp/dbpro-human-verify/*.csv
```

**Expected:** the file exists, is readable, and contains the rows that were in the result grid —
export availability follows the **result state**, not merely editor text (run a query that returns
nothing and confirm the behaviour you observe).

**Record:** written observations.

## Phase 4 — Persistence and exit (~5 min)

### Step 18 — Quit with ⌘Q, then relaunch

1. With the SQLite and PostgreSQL connections open (and, if you like, a dirty draft or a staged change
   left in the grid), quit with **⌘Q**.
2. Confirm the process is gone:

```bash
pgrep -fl db-pro-native || echo "no process — clean exit"
```

   **Expected:** no output from `pgrep` (no lingering process, no crash dialog).

3. Relaunch the same `.app` (`open "/tmp/dbpro-human-verify/DB Pro.app"`).
4. Verify persistence: the saved connections are still listed (this is the interactive persistence
   check — file-level reuse was already verified, but a *saved connection surviving relaunch* is
   what this step proves), the theme is still **Light**, and the workspace comes up without a blank
   screen or orphan-tab crash.

**Known limitation to expect, not a defect:** workspace/tab restore does **not** exist in the
shipping build (`R-015`; eframe persistence is off), so tabs will be gone after relaunch. Write
that down rather than treating it as a failure. Likewise, staged changes must **not** be applied
automatically on restart — confirm they are not.

5. Also confirm the state directory behaves as documented — `~/Library/Application Support/DB Pro`
   is used, `/.db-pro-data` does not appear, nothing is written inside the bundle, and an existing
   `meta.db` was reused rather than recreated:

```bash
ls -la "$HOME/Library/Application Support/DB Pro" ; ls -la /.db-pro-data 2>&1 | head -1
```

**Record:** written observations; note whether a Keychain prompt appeared at any launch.

### Step 19 — Credential persistence, edit and delete (#126)

The secret lifecycle is source-audited in `docs/release/audit-keyring-secret-lifecycle.md`; these are the
packaged-runtime observations that audit cannot produce. Do them on the relaunch from Step 18.

1. **Save → relaunch → connect without retyping.** Reopen the saved PostgreSQL connection and press
   Connect **without entering a password**.

   **Expected:** it connects. The password lives in the OS keyring (macOS Keychain / Linux Secret Service /
   Windows Credential Manager), not in `meta.db`.

   **Record if it fails:** the exact error text. `authentication failed: password not found in secret
   store` means the earlier save did **not** reach the OS store — that is finding **K-1** in the audit
   (a keyring write failure is currently swallowed, so the save looked successful). Also record whether a
   Keychain authorization prompt appeared and whether it was dismissed (`R-KEYRING-STALL`, LIM-018).

2. **Edit with a blank password.** Open the connection's edit dialog, change the **Host** field only, leave
   the password field blank (its hint reads "Leave blank to keep saved password"), save, then connect.

   **Expected:** the stored password is kept and reused, so the failure against the changed host is a
   server-side error — not a "no password" error. Record which one appeared.

3. **Delete → relaunch.** Delete the connection (confirm the dialog), quit, relaunch, and open the
   connection list.

   **Expected:** the connection is gone, no stale entry reappears, and no password prompt is raised for a
   connection that no longer exists.

4. **Keyring-unavailable case (one run, then restore).** Deny the macOS Keychain prompt, or on Linux run
   with no Secret Service present, then repeat 1–3.

   **Expected as the code stands:** the app degrades to the in-memory session store, the connection still
   connects **within the same session**, and after a restart it reports `password not found in secret
   store`. Record **where** the failure appears (save time vs connect time) — the audit predicts connect
   time only, which is finding **K-1** / #243, not a new defect.

**Record:** written observations plus the state-directory listing (`ls -la "$HOME/Library/Application
Support/DB Pro/secrets"` — it must hold no readable password, and in a release build without the opt-in
there should be no `secrets.json` at all).
