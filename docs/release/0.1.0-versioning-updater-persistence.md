### Decision D1 — update delivery model (already decided in the tree, recorded here)

**v0.1 = manual updates: the user downloads a new archive and replaces the binary.** No updater,
no auto-update, no update endpoint. Signed/notarized updates are a post-v0.1 decision that depends
on #103 (identity) and the signing workstream.

## 3. Persisted-state compatibility

### What is actually persisted in v0.1

| Store | Path derivation | Versioning / migration |
|---|---|---|
| Meta store (`meta.db`, SQLite) | `<data-dir>/meta.db` (`crates/runtime/src/lib.rs:121`) | `schema_version` table + ordered migration registry, `LATEST_VERSION = 2` (`crates/infrastructure/src/meta/migration.rs:21,26-41`); idempotent apply; partially-applied v2 is self-healing (`:73-97`); **downgrade blocked**: `current > LATEST_VERSION` → `DbError::Internal` (`:61-64`) |
| Secret store fallback | `<data-dir>/secrets/secrets.json` (`lib.rs:118-119`) | shape is a simple map; keyring is primary in release builds (#142) |
| Keyring entries | service `com.dbpro.app` (`lib.rs:62`) | no versioning; keys stable since introduction |
| eframe window/state storage | keys `dbpro.native.*` (`crates/ui/src/app.rs:445-471`) | **not persisted in v0.1** — `NativeOptions` (`crates/native-app/src/main.rs:313-319`) enables no persistence; LIM-016. The `App::save` writes are in-memory only |
| Query history, saved queries, workspaces | meta store tables (see migration v1→v2) | covered by the meta migrations |

### Data-directory resolution across version/name changes

`resolve_data_dir` (`crates/native-app/src/main.rs:137-168`): `DB_PRO_DATA_DIR` override →
existing cwd-local `.db-pro-data` → platform dir (`~/Library/Application Support/DB Pro`,
`%APPDATA%\DB Pro`, `$XDG_DATA_HOME|~/.local/share/db-pro`) → cwd fallback. Precedence is
already tested (`main.rs:350-392`). Consequence: **legacy beta/dev installs that keep their
`.db-pro-data` keep working on upgrade** because the existence check precedes the platform dir.

### Decision D2 — persisted-state compatibility policy (proposed; owner-confirmed rows cited)

Recorded as the v0.1 policy, pending owner sign-off:

1. **The meta store is the only versioned persistence.** Any schema change ships as an appended
   migration with a bumped `LATEST_VERSION`; applied migrations are never edited
   (`migration.rs:18-23` already states this rule).
2. **Downgrade is refused, not corrupted** — a newer `schema_version` produces a hard error, not a
   silent truncation. This is the current behaviour and the policy keeps it.
3. **JSON-shaped persistence outside the meta store** (eframe storage) is not live in v0.1
   (LIM-016). When persistence is enabled post-v0.1, its keys must follow the brand inventory
   (`docs/release/brand-rename-inventory.md` K12): keep the app id or add read-old/write-new.
4. Data-directory and keyring identifiers follow the same inventory (§3 K1, K3-K6): no blind
   rename; `MIGRATE WITH FALLBACK` rows get the one-time-marker migration described there.

### Decision D3 — legacy beta/dev state (owner decision — PENDING, options recorded)

Current behaviour: legacy `.db-pro-data` is found and reused (D-data-dir row above); meta
migrations v1→v2 apply in place; no reset path exists. Options for v0.1:

- **(a) Migrate and keep** (recommended): the existing behaviour is the policy; nothing is reset.
- **(b) Migrate, keep backup**: on first v0.1 run against pre-v0.1 state, copy `meta.db` to
  `meta.db.pre-v01.bak` before applying migrations.
- **(c) Reset allowed**: pre-v0.1 dev state may be discarded; ship a first-run wipe behind a
  confirmation.

Owner decision recorded in `docs/release/0.1.0-human-decisions.md` when made.

### Decision D4 — version source of truth (already decided in the tree, recorded here)

`crates/native-app/Cargo.toml` `version` is the single release version; the release workflow
derives `app_version` from it and cross-checks the tag (`release.yml:136-153`). The other five
crate manifests are *not* synchronized automatically — for v0.1 they all read `0.1.0`; the rule
for future releases (workspace-level `[workspace.package] version` + `version.workspace = true`
inheritance, or a check script) needs a focused follow-up only if the crate set grows.

### Decision D5 — bundle/app identifier stability after public release (owner decision — PENDING)

`com.dbpro.app` (`tauri.conf.json:4`, keyring service `lib.rs:62`/`main.rs:198`) is the identity
anchor. Two options: keep it after rename (macOS keyring + persisted namespaces survive) or change
it with the K1/K12 migrations from the brand inventory. This belongs to #101/#103; recorded here so
#106 knows the field and #102/#103 know the consequence.

## 4. Downgrade / rollback expectations

- Same-version or patch-bump reinstall: data dir found by precedence, meta migrations idempotent.
- Downgrade to a build with a smaller `LATEST_VERSION`: hard, explicit error from `migrate()`
  (never silent data mangling).
- Rollback of a rename: relaunching the previous build keeps working because the legacy dir is
  never deleted (brand inventory migration rules).
