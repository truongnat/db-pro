==============================================================================
2. ROOT CAUSE
==============================================================================
The shipping crate's credential backend is the D-Bus Secret Service, and its Rust dependency chain
needs the D-Bus *development* file `dbus-1.pc` on Linux at compile time.

Chain, verified locally with the locked graph for the shipped target
(`cargo tree -p db-pro-native --offline --locked --target x86_64-unknown-linux-gnu -e normal,build
-i libdbus-sys`):

    libdbus-sys v0.2.7
    └── dbus v0.9.12
        └── dbus-secret-service v4.1.0
            └── keyring v3.6.3
                ├── db-pro-infrastructure v0.1.0
                │   └── db-pro-runtime v0.1.0
                │       └── db-pro-native v0.1.0
                └── db-pro-native v0.1.0

  * `crates/native-app/Cargo.toml` declares
    `keyring = { version = "3", features = ["apple-native", "windows-native", "sync-secret-service"] }`.
  * `crates/infrastructure/Cargo.toml` uses `keyring.workspace = true`; the workspace features are
    `["apple-native", "linux-native-sync-persistent", "windows-native"]`.
  * In keyring 3.6.3's own manifest (`~/.cargo/registry/src/.../keyring-3.6.3/Cargo.toml`),
    `sync-secret-service = ["dep:dbus-secret-service"]` and
    `linux-native-sync-persistent = ["linux-native", "sync-secret-service"]` — so *both* keyring
    consumers resolve to the libdbus-based backend on Linux. (The zbus-based `secret-service` crate
    is not in this graph: `cargo tree -p db-pro-native --target x86_64-unknown-linux-gnu` contains
    no `secret-service`, `zbus` appears only under accesskit/atspi/ashpd.)
  * `libdbus-sys` 0.2.7 has a build-dependency on the `pkg-config` crate and its build script
    panics when the `dbus-1` pkg-config file is missing — the panic quoted in section 1.

Why the same commit passed `Pre-flight checks` on the same runner image but failed `Build (Linux)`:
the preflight list is larger and includes `libgtk-3-dev`, and on Ubuntu that package reaches
`libdbus-1-dev` transitively:

    libgtk-3-dev -> libatk-bridge2.0-dev -> libatspi2.0-dev -> libdbus-1-dev

(`libatspi2.0-dev`'s Depends list contains `libdbus-1-dev`; verified on packages.ubuntu.com for
jammy, the "libatspi2.0-dev" and "libatk-bridge2.0-dev" pages.) The build job's Linux list has no
GTK/WebKit member, so nothing supplied `dbus-1.pc` and the build-script panic was the first error.
A job's dependency list must cover what that job's own compile needs; borrowing the preflight list's
transitive side effects is what broke the release.

Note the target dependency is easy to miss on this host: against the default (macOS) target the same
query prints "nothing to print" — `libdbus-sys` is only in the Linux graph.

4. PER-PACKAGE JUSTIFICATION
==============================================================================
ADDED to both Linux jobs

  libdbus-1-dev — provides `dbus-1.pc`, the file `libdbus-sys`'s build script looks for. Required by
    the actual compile of `-p db-pro-native` via db-pro-native/-infrastructure -> keyring 3.6.3 ->
    dbus-secret-service 4.1.0 -> dbus 0.9.12 -> libdbus-sys 0.2.7 (chain in section 2). This is the
    package the failing run's own hint names, and the direct cause of the panic.
  pkg-config — the tool `libdbus-sys`'s build script (through the `pkg-config` crate, present in the
    Linux graph) uses to locate `dbus-1.pc`. GitHub's ubuntu images ship it today, but that is the
    same kind of undeclared assumption that broke this release; naming it makes each Linux job's
    dependency list sufficient on its own. It is also the probe used by `wayland-sys` and
    `libsqlite3-sys` in the same graph.

KEPT, unchanged (pre-existing four — this change adds no package to them)

  libgl1-mesa-dev — the only package in the kept set that is clearly link-relevant: `glutin_egl_sys`
    and `glutin_glx_sys` link `-lEGL`/`-lGL`. It satisfies them transitively:
    `libgl1-mesa-dev -> libglvnd-dev -> {libegl-dev, libgl-dev, libglx-dev, libgles-dev,
    libopengl-dev}` (verified on packages.ubuntu.com for both jammy and noble, the current
    ubuntu-latest).
  libwayland-dev, libx11-dev, libxkbcommon-dev — cover the eframe/egui windowing stack. Worth
    recording precisely: in this graph the Wayland/X11/XKB loading is `dlopen`-based, not link-time
    (`cargo tree -e features` shows `wayland-sys feature "dlopen"`, `wayland-backend feature
    "dlopen"`, `smithay-clipboard feature "dlopen"`; `xkbcommon-dl` and `x11-dl` resolve their
    libraries at runtime). They are kept because they are the documented eframe Linux requirement,
    because removing packages is out of scope for this fix, and because the passing preflight in the
    same run used the same base list for the same crates.

WHY NO OTHER PACKAGE WAS ADDED (each checked against the graph, not assumed)

  * `-p db-pro-native` on Linux resolves to 346 packages
    (`cargo tree -p db-pro-native --offline --locked --target x86_64-unknown-linux-gnu -e
    normal,build --prefix none`). Filtering that list:
      - `openssl-sys` / `native-tls`: absent (count 0). TLS is rustls everywhere
        (`sqlx ... runtime-tokio-rustls`, `reqwest ... rustls-tls`), so no libssl-dev is required —
        and `dbus-secret-service`'s optional `crypto-openssl` feature is not enabled.
      - `libsqlite3-sys`: present but with `libsqlite3-sys feature "bundled"` activated by
        `rusqlite feature "bundled"` (verified with `cargo tree -e features -i libsqlite3-sys`);
        SQLite is compiled from bundled C source with `cc`, so no system `libsqlite3-dev`/`sqlite3`.
      - `gtk`, `gtk-sys`, `glib`, `webkit2gtk`, `soup3`, `libappindicator`: absent. The legacy
        `crates/tauri-app` (which needs them) is not in this job's build set, so the WebKit/GTK
        headers stay preflight-only. The file picker is `rfd 0.15.4`, which on Linux uses the XDG
        portal path (`rfd feature "xdg-portal"` / `"ashpd"`, D-Bus over zbus — no pkg-config, no
        GTK); the `gtk-sys` edge belongs to `rfd 0.16.0`, pulled only by `tauri-plugin-dialog`.
      - `libegl1-mesa-dev`: not added — already reached through `libgl1-mesa-dev -> libglvnd-dev ->
        libegl-dev` (section above).
  * The first release run reached its link stage only in preflight. The strongest available
    cross-check that the four kept packages are the right set for this job is that preflight — same
    ubuntu-latest image, same four base packages plus GTK — both compiled *and linked* the same
    crates in the same run via `cargo test --workspace` (which links the test harnesses of every
    workspace member, including db-pro-native's). The release build links the same crates on the
    same image; with `dbus-1.pc` present its link inputs are the ones preflight already exercised.

7. RESIDUAL RISK FOR THE WINDOWS / LINUX JOBS (cannot be executed here)
==============================================================================
  1. Linux link stage: the release `build` job has not yet been observed green on Linux (this run
     died in a dependency build script, before linking). The four kept packages plus dbus are
     expected to suffice — preflight linked the same crates on the same image in the same run, and
     the EGL/GL dev files are reached from `libgl1-mesa-dev` (section 4) — but the re-run is the
     first direct proof.
  2. Runner image drift: `ubuntu-latest` is a moving label (`libgl1-mesa-dev`/`libatspi2.0-dev`
     dependency chains were checked for jammy and noble). A future image change could alter either
     chain; the packaging contract already records the moving Windows/Linux labels as a known
     limitation (0.1.0-packaging.md §2).
  3. `sudo apt-get install` requires network access to the Ubuntu mirrors in both Linux jobs; a
     transient mirror failure fails the job loudly rather than silently.
  4. If the credential backend changes, the package set must follow: keyring's
     `linux-native-async-persistent` would pull the zbus-based `secret-service` crate (no
     libdbus-sys, so `libdbus-1-dev` would no longer be needed), and enabling
     `dbus-secret-service/crypto-openssl` would add `openssl-sys` (needs `libssl-dev`). Neither is
     active today — checked, not assumed.
  5. Windows job: unaffected by this commit (only the Linux-only step and preflight's apt step
     changed; no Windows dev package is implicated by the graph). Residual Windows risk is the
     pre-existing MSVC/keyring-windows-native set, unchanged and unverifiable here.
  6. Pre-existing and out of scope: preflight's fmt/clippy/test steps still run without `--locked`
     (recorded as PARTIAL in 0.1.0-packaging.md §2).
