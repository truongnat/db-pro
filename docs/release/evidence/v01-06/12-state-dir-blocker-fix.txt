==============================================================================
2. ROOT CAUSE
==============================================================================
`resolve_data_dir()` (crates/native-app/src/main.rs:127-135 before this change) was

    std::env::var_os("DB_PRO_DATA_DIR")
        .map(std::path::PathBuf::from)
        .unwrap_or_else(|| {
            std::env::current_dir()
                .expect("current directory is available")
                .join(".db-pro-data")
        })

A bundle launched by LaunchServices/Finder inherits `cwd=/` (verified again below with
`lsof -a -p <pid> -d cwd` -> `cwd DIR 1,16 704 2 /`), so the fallback resolved to `/.db-pro-data`.
A normal user cannot create a directory at the volume root, so
`DbProRuntime::new` -> `std::fs::create_dir_all(&data_dir)` returned
`RuntimeInitError::CreateDataDir(Os { code: 30, kind: ReadOnlyFilesystem, .. })`,
`main() -> Result<(), Box<dyn Error>>` propagated it, and the process exited with status 1
**without ever opening a window**. Because the app exits silently from the user's point of view,
`open` returning 0 ("LaunchServices accepted the bundle") says nothing about whether the app
stays up — the earlier "LaunchServices-accepted" claim recorded in
`03-release-binary.txt` / `08-post-fix-quality-gates.txt` was misleading in exactly that way
(corrected by an appended note in both files; the original text is preserved).

3. THE FIX — EXACT BEFORE / AFTER
==============================================================================
Resolution order after the change:

  1. `DB_PRO_DATA_DIR`, when set and non-empty            -> used verbatim (unchanged behaviour)
  2. `<cwd>/.db-pro-data` when it *already exists* as a  -> used (developer checkout / existing
     directory                                              installs keep their data in place)
  3. `<platform data dir>/DB Pro` (macOS: `$HOME/Library/Application Support/DB Pro`;
     Windows: `%APPDATA%\DB Pro`; other Unix: `$XDG_DATA_HOME/db-pro`, else
     `$HOME/.local/share/db-pro`)
  4. `<cwd>/.db-pro-data`, or the relative `.db-pro-data` when the working directory cannot be
     resolved — no `expect(...)` panic any more.

3.1 New code (crates/native-app/src/main.rs, replacing the old body)

    /// Name of the legacy, working-directory-local state directory.
    const LEGACY_DATA_DIR_NAME: &str = ".db-pro-data";
    /// Application directory name used inside the per-user platform data root.
    const PLATFORM_APP_DIR_NAME: &str = "DB Pro";

    fn resolve_data_dir() -> std::path::PathBuf {
        let override_dir = non_empty_env("DB_PRO_DATA_DIR").map(std::path::PathBuf::from);
        let cwd = std::env::current_dir().ok();
        let legacy_exists = cwd
            .as_deref()
            .is_some_and(|dir| dir.join(LEGACY_DATA_DIR_NAME).is_dir());

        choose_data_dir(override_dir, cwd.as_deref(), legacy_exists, platform_data_dir())
    }

    fn choose_data_dir(
        override_dir: Option<std::path::PathBuf>,
        cwd: Option<&std::path::Path>,
        legacy_exists: bool,
        platform_dir: Option<std::path::PathBuf>,
    ) -> std::path::PathBuf {
        if let Some(dir) = override_dir {
            return dir;
        }
        if legacy_exists {
            if let Some(dir) = cwd {
                return dir.join(LEGACY_DATA_DIR_NAME);
            }
        }
        if let Some(dir) = platform_dir {
            return dir;
        }
        cwd.map(|dir| dir.join(LEGACY_DATA_DIR_NAME))
            .unwrap_or_else(|| std::path::PathBuf::from(LEGACY_DATA_DIR_NAME))
    }

    fn platform_data_dir() -> Option<std::path::PathBuf> {
        if cfg!(target_os = "macos") {
            non_empty_env("HOME").map(|home| {
                std::path::PathBuf::from(home)
                    .join("Library").join("Application Support").join(PLATFORM_APP_DIR_NAME)
            })
        } else if cfg!(target_os = "windows") {
            non_empty_env("APPDATA")
                .map(|appdata| std::path::PathBuf::from(appdata).join(PLATFORM_APP_DIR_NAME))
        } else {
            non_empty_env("XDG_DATA_HOME")
                .map(std::path::PathBuf::from)
                .or_else(|| non_empty_env("HOME")
                    .map(|home| std::path::PathBuf::from(home).join(".local").join("share")))
                .map(|data_root| data_root.join("db-pro"))
        }
    }

    /// Reads an environment variable, treating an empty value as unset.
    fn non_empty_env(key: &str) -> Option<std::ffi::OsString> {
        std::env::var_os(key).filter(|value| !value.is_empty())
    }

The decision itself is the pure `choose_data_dir` function: it takes the override, the working
directory, a *pre-computed* "legacy directory exists" boolean and the platform directory, and
touches no process-global state. `resolve_data_dir()` is the thin environment wrapper, so the
tests never mutate the process environment.

6. SEPARATE, PRE-EXISTING STARTUP DEPENDENCY FOUND WHILE DOING THIS (NOT FIXED HERE)
==============================================================================
Both launch paths above (via `open` and directly from this shell) initially *blocked* inside
`seed_groq_api_key_from_keyring()` -> `keyring::Entry::get_password()` ->
`SecKeychainFindGenericPassword` -> securityd (`mach_msg` wait). Stack samples:
  /tmp/dbpro-fix/sample-run1.txt      (open-launched, pid 15873)
  /tmp/dbpro-fix/sample-direct-run.txt (direct cwd=/ run without the bypass, pid 32302)

This is not the data-directory defect and not a regression:
  * the call already sat before `resolve_data_dir()` in `main()` before this change, and its code
    is untouched (`crates/native-app/src/main.rs`, function `seed_groq_api_key_from_keyring`);
  * it is environment-dependent: the coordinator's pre-fix reproduction reached `CreateDataDir`,
    which means the keyring read returned in that run; here it waited on a Keychain authorization
    request for the developer's *existing* `com.dbpro.app` / `agent/groq_api_key` item, which an
    ad-hoc-signed binary cannot read without an interactive grant. Whether it blocks or returns
    depends on how that prompt is answered, not on the code path.
  * it is the reason the artifact proof in 5.3/5.4/5.5/5.6 sets `GROQ_API_KEY` to an inert dummy
    value: `seed_groq_api_key_from_keyring()` returns immediately when the variable is already set,
    which isolates the state-directory behaviour under test. No other behaviour changes.

Consequence for the release: a user whose Keychain holds a DB Pro item will see a Keychain
authorization prompt on first launch of the packaged app, and an *unattended* launch (automation,
CI, or a user who never answers) can wait indefinitely at that prompt. This is a distinct item from
`R-STATE-DIR`; it is flagged here for the coordinator and is NOT fixed in this change (it is a
keyring/UX decision, and the instruction for this run was to leave the rest of `main.rs` alone).
No credential was read, written, printed or deleted by this run.
