==============================================================================
2. ROOT CAUSE
==============================================================================
The release was qualified on rustc 1.95.0, but nothing in the repository pinned the compiler:

  * rust-toolchain.toml declared `channel = "stable"` — a moving target. GitHub's `stable` is currently
    1.98.0, so the same commit is compiled by a different compiler in CI than on the release machine.
  * release.yml installed `dtolnay/rust-toolchain@stable`, i.e. it explicitly asked for the floating
    channel instead of honouring the toolchain file (the action installs the requested toolchain; the
    workflow never asserted which compiler ended up active).
  * clippy 1.98 added/beefed up `result_large_err`, which fires at the site above. The codebase already
    carries five targeted exemptions for this lint (verification below), but not at that site.

Consequence: with no repository change at all, a locally green quality gate (and the release binary
built from it) turned red in CI, and any artifact produced by CI would have been built by a compiler the
V01-06 evidence does not cover.

3.2 .github/workflows/release.yml — preflight job (was lines 190-192) and build job (was lines 295-297)

    BEFORE (both jobs, identical):
        - uses: dtolnay/rust-toolchain@stable
          with:
            components: rustfmt, clippy

    AFTER (both jobs, identical run body):
        # Reproducibility (goal-3 §15): the release must compile with the exact
        # compiler it was qualified on. rust-toolchain.toml in the checked-out
        # candidate is the single source of truth — no second copy of the version
        # is hard-coded here. A non-exact pin, or an active rustc that does not
        # match it, fails the job instead of silently falling back to the runner's
        # floating `stable`.
        - name: Install pinned Rust toolchain
          shell: bash
          run: |
            set -euo pipefail

            pinned_channel="$(sed -n 's/^[[:space:]]*channel[[:space:]]*=[[:space:]]*"\([^"]*\)".*/\1/p' rust-toolchain.toml)"
            if [[ -z "${pinned_channel}" ]]; then
              echo "::error::rust-toolchain.toml does not declare a toolchain channel"
              exit 1
            fi
            if [[ ! "${pinned_channel}" =~ ^[0-9]+\.[0-9]+\.[0-9]+$ ]]; then
              echo "::error::rust-toolchain.toml channel '${pinned_channel}' is not an exact version pin; a release must not build with a floating toolchain"
              exit 1
            fi

            rustup toolchain install "${pinned_channel}" \
              --profile minimal \
              --component rustfmt \
              --component clippy
            rustup default "${pinned_channel}"

            rustup show active-toolchain
            rustc --version --verbose
            cargo clippy --version

            active_version="$(rustc --version | awk '{print $2}')"
            if [[ "${active_version}" != "${pinned_channel}" ]]; then
              echo "::error::Active rustc ${active_version} does not match pin ${pinned_channel} from rust-toolchain.toml"
              exit 1
            fi
            echo "Pinned toolchain active: rustc ${active_version}"

7. PROOF THAT THE RELEASE BUILD CANNOT SILENTLY USE `stable`
==============================================================================
Which command establishes the version: the new step's first line reads the pin out of the candidate
tree — `pinned_channel="$(sed -n 's/^[[:space:]]*channel[[:space:]]*=[[:space:]]*"\([^"]*\)".*/\1/p' rust-toolchain.toml)"`
(value today: 1.95.0) — then `rustup toolchain install "${pinned_channel}" --profile minimal
--component rustfmt --component clippy` provisions exactly that toolchain, `rustup default
"${pinned_channel}"` makes it the default as well as the directory override, and finally
`active_version="$(rustc --version | awk '{print $2}')"` is compared for exact equality against the pin.

Why it cannot fall back silently:
  a) The asserted quantity is the *compiler itself* (the version token printed by rustc), not the exit
     status of an installer step and not a channel label. If the active rustc is not exactly the pinned
     version, the step prints `::error::` and exits 1 under `set -euo pipefail`, failing the job before
     fmt/clippy/test in preflight and before the build on all three platforms.
  b) The number exists in exactly one place (rust-toolchain.toml). Nothing in the workflow hard-codes it,
     so a bump cannot leave the workflow pointing at the old compiler.
  c) Reverting the file to a floating channel is itself a hard failure: `channel = "stable"` fails the
     exact-version guard instead of silently re-enabling the floating compiler (scenario B below).
  d) There is no other toolchain selection left in the workflow (no `dtolnay/rust-toolchain`, no
     `RUSTUP_TOOLCHAIN` env in any `env:` block), so nothing can re-point the compiler after this step.
  e) rustup's own behaviour is a second backstop: if the pinned toolchain cannot be provisioned, rustup
     exits non-zero rather than substituting another toolchain (scenario D below).

Dry-run evidence — the shipped script was extracted from the YAML (sha256 d41c49f2..., identical for
both jobs) and executed on this host, against real rustup, in a throwaway directory outside the repo:

8. WHAT COULD STILL FAIL ON WINDOWS / LINUX (cannot be executed on this macOS host)
==============================================================================
  1. `shell: bash` on `windows-latest` is Git Bash: the step needs `rustup`, `rustc`, `cargo` on PATH
     inside bash. GitHub-hosted Windows images put `~/.cargo/bin` on PATH and propagate it to bash steps,
     and the pre-existing `Report Rust toolchain` step already relied on the same assumption — but this
     is unverified here. Failure mode would be a loud "command not found" (exit 127 under `set -e`), not
     a silent wrong compiler.
  2. The step now downloads a second toolchain on each runner (~200-400 MB per platform) instead of
     reusing the preinstalled `stable`. Hosted runners have network access to static.rust-lang.org; an
     egress restriction would fail the job loudly (scenario D) rather than fall back.
  3. Host triples assumed available upstream: `x86_64-unknown-linux-gnu` (ubuntu-latest),
     `x86_64-pc-windows-msvc` (windows-latest), `aarch64-apple-darwin` (macos-14). All are tier-1 hosts
     for the pinned release; the assertion compares only the version token, so it is host-independent.
  4. `actions/cache` caches `target/` under a key that does not include the toolchain version
     (`${{ runner.os }}-cargo-${{ hashFiles('**/Cargo.lock') }}`). This is safe — rustc fingerprints
     include the compiler version, so artifacts are rebuilt rather than reused across compilers — but it
     does mean the first run after this pin pays a full rebuild on each platform. Left unchanged on
     purpose (out of scope).
  5. Pre-existing, unrelated, out of scope: `ci.yml` is red on `main` because of an escaped-quote bug in
     the Python one-liner in its `Configure live SSH backup fixture` step. That workflow is untouched
     here and does not gate the release workflow, but it will keep failing until fixed separately.
  6. Follow-up to record (deliberately NOT fixed here): the `clippy::result_large_err` finding at
     table_data_service.rs:222 is real under clippy 1.98. Pinning 1.95.0 restores reproducibility but
     does not make the codebase 1.98-clean; when the pin is eventually bumped, that site needs either a
     targeted `#[allow]` (matching the five existing ones) or an error-type change, under review.
