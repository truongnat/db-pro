## 1. The v0.1 packaging contract (decision §5)

**Decision: Option A + a macOS `.app` wrapper** — portable native archives plus one checksum
manifest, no installers.

| Artifact | Contents |
|---|---|
| `db-pro-v0.1.0-macos-arm64.tar.gz` | `DB Pro.app/Contents/MacOS/db-pro-native`, `DB Pro.app/Contents/Info.plist`, `README-INSTALL.txt` |
| `db-pro-v0.1.0-windows-x86_64.zip` | `db-pro-native.exe`, `README-INSTALL.txt` |
| `db-pro-v0.1.0-linux-x86_64.tar.gz` | `db-pro-native` (mode 755), `README-INSTALL.txt` |
| `SHA256SUMS.txt` | SHA-256 of the three archives (assembled by the `checksums` job) |
| `db-pro-provenance-v0.1.0-<short-sha>` | `release-provenance.json` (version, SHA, ref, event, rustc, binary) |

Implemented by `.github/workflows/release.yml` (`resolve` → `preflight` → `build` → `package` →
`checksums`) and the scripts under `scripts/release/`:

| Script | Purpose |
|---|---|
| `scripts/release/package-macos.sh` | builds the `.app` bundle (generates `Info.plist`, derives `LSMinimumSystemVersion` from `otool -l` `LC_BUILD_VERSION` minos, currently **11.0**), tars with `--no-mac-metadata` |
| `scripts/release/package-linux.sh` | tars the binary + install note |
| `scripts/release/package-windows.ps1` | `Compress-Archive` of the `.exe` + install note |
| `scripts/release/write-checksums.sh` | writes/validates `SHA256SUMS.txt` |
| `scripts/release/README-INSTALL.txt` | the install note shipped inside every archive |

Why not installers: `.dmg`, MSI/NSIS, `.deb`/`.rpm` and AppImage each introduce a packaging
ecosystem (and, unsigned, more trusted-looking-but-unverified artifacts) without resolving any
actual blocker. The four real blockers are license, brand name, signing and unfinished runtime
evidence — none of them is "we lack an installer".
(`docs/release/evidence/v01-06/05-workflow-audit.md` §3.)

Workflow properties that matter: `permissions: contents: read` (it cannot create a Release or
push a tag), **no `secrets.*`**, the ref is resolved to an exact 40-char SHA and re-verified in
the checkout, a `v*` tag must match `crates/native-app/Cargo.toml`, and each platform's
architecture is asserted (`lipo -archs` = `arm64`; PE machine `0x8664`; ELF `x86-64`).

**Status:** artifact names/checksums from the in-flight run are `PENDING_CI_RUN_RE_DISPATCH` — the
earlier run `34847235273` built the pre-fix candidate (it also produced the Linux build failure
fixed by `e22a498`) and is superseded by the `543b526` state-directory fix, so it must be
re-dispatched for the current HEAD (`risk-register.md` §4). Local equivalents were produced; the
macOS one is now verified beyond process level — after `543b526` an `open`-launched bundle stays
alive past 30 s, creates its per-user state directory and no longer exits with `CreateDataDir`
(`docs/release/evidence/v01-06/12-state-dir-blocker-fix.txt` §5). No window was rendered or
interacted with, and the interactive install smoke is still pending.

### Intentional deferrals

| Deferred | Why |
|---|---|
| macOS `.dmg` | needs signing to be non-hostile; adds `hdiutil` nondeterminism; not required to launch |
| Windows MSI / NSIS | WiX/NSIS toolchains; unsigned installers raise SmartScreen just like a zip |
| Linux `.deb` / `.rpm` / AppImage | distro dependency declarations (including the D-Bus Secret Service question) and FUSE complications |
| macOS x86_64 artifact | not in the matrix; Intel Macs have no artifact |
| Universal binary | needs both slices built |
| Code signing / notarization | no certificate; see §5 |
| Auto-update | out of scope for v0.1 |

### Per-platform native requirements

| Platform | Build-time | Runtime |
|---|---|---|
| macOS | Xcode command line tools | none beyond the OS; the binary links only `/System` and `/usr/lib` (`otool -L`), minimum macOS 11.0 |
| Windows | MSVC build tools | MSVC runtime (`vcruntime140.dll`, normally present); Credential Manager for the keyring |
| Linux | `libxkbcommon-dev libwayland-dev libx11-dev libgl1-mesa-dev libdbus-1-dev pkg-config` (the whole-workspace preflight additionally installs WebKit/GTK headers because the legacy `crates/tauri-app` is still a workspace member; both Linux jobs now name the D-Bus/pkg-config packages explicitly instead of borrowing them from `libgtk-3-dev`) | X11 or Wayland + a working OpenGL driver + `libdbus-1`; **a D-Bus Secret Service provider (gnome-keyring/KWallet)** for credential storage — the shipping crate enables `sync-secret-service`. Headless installs will fail credential writes. `pg_dump`/`pg_restore`/`ssh` on `PATH` for backup and SSH features. |

The Linux build-time list above mirrors what `release.yml` installs in *both* Linux jobs
(`Install Linux system deps` in `build`, `Install system dependencies` in `preflight`).
`libdbus-1-dev`/`pkg-config` are a **build** dependency of the credential backend: the shipping
crate's `keyring` backend (`dbus-secret-service` → `dbus` → `libdbus-sys`) probes `dbus-1.pc` and
its build script panics without it (release run `34847235273`, job `Build (Linux)`). The same
D-Bus Secret Service stack is also the expected **runtime** credential service on Linux — the
binary links `libdbus-1` and credential storage needs a Secret Service provider on the session
bus. See `docs/release/evidence/v01-06/11-linux-build-dependency-fix.txt`.

## 2. Reproducibility (§15)

| Requirement | State | Evidence |
|---|---|---|
| `Cargo.lock` present and tracked | PASS | tracked; `--locked` used by the release build (`release.yml` build step) and by `ci.yml` |
| `--locked` on every gate | PARTIAL | the release build uses `--locked`; the preflight `fmt`/`clippy`/`test` steps do not (low severity: a preflight could pass against an unlocked resolution) |
| No floating git dependencies | PASS | `grep 'source = "git' Cargo.lock` → no matches; everything resolves from crates.io |
| No runtime asset downloads at launch | PASS | fonts are `include_bytes!`-compiled (`crates/ui/src/theme.rs`), SQLite is bundled (`rusqlite` feature `bundled`), TLS is rustls; the only network use is the optional Agent provider call |
| No local absolute paths in source/config | PASS | no `/Users/...` in `.rs`/`.toml`/`.json`/`.yml`/`.sh` outside `target/` |
| Fresh checkout builds | PASS (macOS ARM64, measured) | all six gates from this checkout (`02-quality-gates.txt`, `08-post-fix-quality-gates.txt`) |
| Toolchain pinned | PASS | `rust-toolchain.toml` = **1.95.0**; `release.yml` reads the file, installs that exact toolchain and fails if the active `rustc` differs (`09-toolchain-pinning.txt`) |

Known non-reproducibility, stated rather than hidden:

- **Archives are not bit-reproducible** (mtimes are embedded by `tar`/`Compress-Archive`); the
  *binary* is built from a locked dependency graph on a pinned compiler, but the container
  format is not.
- The binary embeds **absolute Cargo registry build paths** from Rust panic `Location` metadata
  (e.g. `/Users/<builder>/.cargo/registry/src/index.crates.io-…/winit-0.30.13/…`). Not a
  credential, but it discloses the builder's home directory; avoidable with
  `--remap-path-prefix`.
- The macOS runner is pinned to `macos-14` precisely so the produced architecture cannot change
  under the project; the Windows/Linux runners are still moving labels.

## 3. Secrets and credentials (§16)

Audit method: `git grep` over tracked files with high-signal credential patterns (private-key
headers, `sk-…`, `ghp_…`/`gho_…`, `AKIA…`, `xox…`, `AIza…`), heuristic
`password|secret|api_key|token = "…"` matching, inspection of the local runtime state directory,
and `strings` over the release binary. Values are not reproduced here. Full table:
`docs/release/evidence/v01-06/05-workflow-audit.md` §8.

| Result | Detail |
|---|---|
| Private keys / `sk-` / `ghp_` / `AKIA` / `xox` / `AIza` in tracked files | **none** — clean |
| Secrets in either workflow | **none** — `release.yml` and `ci.yml` reference no `secrets.*`; only `vps-pr-review.yml` uses the auto-provided `GITHUB_TOKEN` |
| Fixture credentials (`dbpro`/`dbpro_test`, `postgres/postgres`) | test-only, confined to `fixtures/`, `docker-compose.yml` and CI; CI generates ephemeral SSH keys into `$RUNNER_TEMP` and never commits them |
| Test sentinel (`should-not-cross-boundary`) | inside `#[cfg(test)]`, test-only |
| User credential store (`.db-pro-data/secrets/secrets.json`) | **not tracked** (`.gitignore`), file mode 0600 |
| User metadata DB (`.db-pro-data/meta.db`) | **not tracked**; connection rows store `config` + a `secret_ref` indirection, not the raw password |
| Provider keys | only env-var *names* appear in the binary (`GROQ_API_KEY`, `OPENAI_API_KEY`, …); no key values |

Resolved findings:

- **Developer-preset leak — `FIXED` (`c682552`).** The production default used to pre-fill a
  developer connection (label, private database name, tag, user, password) and seed it at
  startup; it is now `#[cfg(debug_assertions)]`-only, and the shipped binary no longer contains
  the database name, tag, credentials or the log text naming them. Release-profile tests assert
  the absence (`developer_connection_preset_is_gated_to_debug_builds`,
  `default_draft_identity_follows_build_profile`).
- **Component-gallery label — `FIXED` (`7794196`).** The gallery no longer renders the developer
  connection label. One residual "Xe Lạc Hồng" string remains as demo text for
  ConnectionIndicator/StatusBarItem/ContextChip; it carries no host, database, user or
  password.

**Packaging rule (binding):** archives are built from the binary in `target/release/` (or from a
fresh checkout / `git archive`) — **never** by copying the working tree. The working tree
contains `.db-pro-data/` (real connection metadata + credential store), `target/`,
`fixtures/`, `docker-compose.yml`, `.env*` and tool/session state directories, all of which must
stay outside any archive.

## 4. Release data / migration safety (§17)

State layout, as implemented:

```text
<data dir>/
  meta.db                 # SQLite workspace store
  secrets/                # KeyringVault encrypted-file fallback (0600)
```

`meta.db` tables: `connections`, `query_history`, `saved_queries`, `saved_query_folders`,
`workspaces`, `settings`, `introspection_cache`, `run_configs`, plus `schema_version`.

| Question | Answer |
|---|---|
| Data a v0.1 install/update must not destroy | connections, saved queries (+folders), query history, workspace records, settings, run configs |
| Where the data dir comes from | `DB_PRO_DATA_DIR` if set and non-empty; otherwise an existing `<cwd>/.db-pro-data`; otherwise the per-user platform data directory (`~/Library/Application Support/DB Pro`, `%APPDATA%\DB Pro`, `$XDG_DATA_HOME/db-pro` else `~/.local/share/db-pro`); otherwise `<cwd>/.db-pro-data` (relative `.db-pro-data` if the working directory is unavailable). `crates/native-app/src/main.rs` — `resolve_data_dir` / `choose_data_dir` / `platform_data_dir`; fixed in `543b526`. |
| Is there a versioned migration mechanism? | **Yes.** `crates/infrastructure/src/meta/migration.rs` holds an ordered `MIGRATIONS` registry with **`LATEST_VERSION = 2`** (v1 = baseline schema, v2 = add `database`/`schema` columns to `query_history`). Applied versions are recorded in `schema_version`; already-applied migrations are skipped (idempotent); a **malformed version row fails closed**; and a database **newer than `LATEST_VERSION` is rejected** rather than opened blindly. |
| Baseline version for a first public release | `schema_version = 2` |
| Upgrading from earlier native dev builds | the v2 migration is additive (`ALTER TABLE … ADD COLUMN`) and is exercised by the migration tests; no down-migration exists |
| Residual risk | there is no automatic pre-migration backup and no downgrade path; a wrong future migration would need manual recovery from a user-side copy. Recorded as `R-STATE-MIGRATION` (`ACCEPTED`). Workspace/tab settings are not persisted at all (`R-015`). |

**Status: `UNSIGNED` on every platform — measured, not assumed.**

| Check | Result |
|---|---|
| macOS signature | `Signature=adhoc`, `flags=0x20002(adhoc,linker-signed)`, `TeamIdentifier=not set`, `Info.plist=not bound` — the linker's automatic ad-hoc signature, **not** a Developer ID |
| macOS notarization | not configured (no `notarytool`/`stapler` step) |
| macOS Gatekeeper | `spctl -a -vvv -t execute` → **rejected** (exit 3) |
| Windows signing | not configured (no `signtool`, no certificate) |
| Linux signing | not configured (no GPG-signed packages; no packages either) |

Expected user-facing effect if 0.1.0 ships unsigned: macOS *"…cannot be opened because the
developer cannot be verified"* (right-click → Open, or Settings → Privacy & Security → Open
Anyway); Windows SmartScreen *"Windows protected your PC"*; Linux no OS-level warning.
No secrets exist in the repository and none were added. Register: `R003` (`ACCEPTED`).

## 6. Startup failure handling (§18)

Measured/source-verified behaviour. "Handled" means the failure produces an error path instead of
a panic or silent data damage.

| Failure | Behaviour | Verdict |
|---|---|---|
| State directory cannot be created | `DbProRuntime::new` → `RuntimeInitError::CreateDataDir`; `main() -> Result<(), Box<dyn Error>>` returns the error (process exits with a message) | **Handled** (no recovery UI). **This path was actually hit by the packaged candidate**: a LaunchServices-launched `.app` runs with `cwd=/`, `current_dir()/.db-pro-data` resolved to `/.db-pro-data` and the app died with `CreateDataDir(Os { code: 30, kind: ReadOnlyFilesystem })` before opening a window. Fixed in `543b526` by resolving a per-user state directory (`R-STATE-DIR`, `12-state-dir-blocker-fix.txt`) |
| Corrupted / malformed `meta.db` (including a malformed `schema_version` row) | fails closed: migration parsing returns `DbError::Internal` and the error propagates out of `SQLiteMetaStore::new` → `DbProRuntime::new` → `main()`; the user's data is not overwritten | **Handled** (fails closed; no repair flow) |
| `meta.db` written by a **newer** app version | explicitly rejected (`schema version N is newer than supported version 2`) | **Handled** (fails closed) |
| Missing font | impossible at runtime — the four Inter TTFs are compiled in with `include_bytes!`; nothing is read from disk | **Not applicable** |
| Invalid workspace state | eframe persistence is **off** and tabs/settings are not restored, so there is no workspace-state parser to feed bad data; nothing is restored and nothing panics. (Implementing persistence will require a fail-safe path — noted for that change.) | **Not applicable today / risk when persistence lands** |
| Missing / stale connection at startup | reconnect is per connection and best-effort; a failed reconnect surfaces as a connection error state and does not block other connections or the app | **Handled as a state, not as a crash** (runtime smoke `PENDING`) |
| Provider key missing (`GROQ_API_KEY`/`OPENAI_API_KEY`) | `seed_groq_api_key_from_keyring()` is best-effort; with no key and none in the keyring the provider is absent and the Agent panel simply cannot generate | **Handled** |
| File picker unavailable/cancelled | picker results are fire-and-forget `UiEvent::FilePicked` with `path: None` | **Handled** |

No startup panic was observed in the binary audit: the release binary launches and idles without
crashing (`03-release-binary.txt`). The one open unknown recorded here earlier — the
working-directory/state-directory question for a LaunchServices-launched `.app` — has since been
**reproduced as a real blocker and fixed**: the app resolved `current_dir()/.db-pro-data`, which is
`/.db-pro-data` under the `cwd=/` a Finder/`open` launch inherits, and exited 1 with
`CreateDataDir(ReadOnlyFilesystem)` before opening a window. `resolve_data_dir()` now resolves
`DB_PRO_DATA_DIR` → existing `<cwd>/.db-pro-data` → per-user platform data directory →
`<cwd>/.db-pro-data` (commit `543b526`). Register `R-STATE-DIR` is `FIXED`; evidence
`docs/release/evidence/v01-06/12-state-dir-blocker-fix.txt`. Still open on the same launch path (a
different, pre-existing dependency): the keyring read in `seed_groq_api_key_from_keyring()` runs
*before* data-directory resolution and waits on a Keychain authorization prompt for an
ad-hoc-signed binary, so an unattended first launch can hang there — recorded in `12-…txt` §6, not
fixed in this pass.
