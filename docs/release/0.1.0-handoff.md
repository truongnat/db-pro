## 7. Install smoke procedure (do this before tagging)

1. Download the three archives from run `34847235273` into one directory and place the run's
   `SHA256SUMS.txt` beside them.
2. Verify checksums: `shasum -a 256 -c SHA256SUMS.txt` (macOS/Linux);
   `Get-FileHash -Algorithm SHA256 <file>` on Windows. Record the output.
3. macOS: `tar -xzf db-pro-v0.1.0-macos-arm64.tar.gz`, then open the extracted `DB Pro.app`.
   Expect the Gatekeeper "cannot be verified" flow (right-click → Open, or System Settings →
   Privacy & Security → Open Anyway). Confirm: window appears, theme renders, no panic; then
   connect to a scratch SQLite file and run `SELECT 1;`.
   **State-directory check (open risk `R-STATE-DIR`):** because the app derives its data
   directory from `current_dir()/.db-pro-data` (`DB_PRO_DATA_DIR` overrides it) and a
   LaunchServices-launched app runs with `cwd=/`, confirm where `.db-pro-data` is created. If
   the app cannot create it, that is a must-fix before publishing — reproduce with
   `cd / && /Applications/DB\ Pro.app/Contents/MacOS/db-pro-native`.
4. Windows: extract the `.zip`, run `db-pro-native.exe`, accept SmartScreen's "Run anyway",
   repeat the SQLite `SELECT 1;` check.
5. Linux: extract the `.tar.gz`, `./db-pro-native` on a desktop session with X11/Wayland + GL and
   a running Secret Service (gnome-keyring/KWallet); confirm a connection can be saved
   (credential write) and re-opened.
6. Record results in `docs/release/0.1.0-manual-smoke.md` (tick items and fill the sign-off at
   the candidate SHA) and update this document's §5 table. Do not tick anything you did not run.

## 8. Tag / release steps

The workflow is prepared for tagging but **no tag exists**. Sequence once §7 and the license
decision are settled:

1. Confirm the working tree is clean at the candidate SHA: `git status --porcelain -uall`
   should show only `goal-3.md` (untracked planning input, intentionally not committed).
2. Create an annotated tag: `git tag -a v0.1.0 fbf9fdab9100f08f12e29434983f32c18f14ac2f -m "DB Pro 0.1.0"`.
   The workflow rejects a `v*` tag whose version differs from `crates/native-app/Cargo.toml`.
3. Push the tag: `git push origin v0.1.0` — this triggers `release.yml` (tag push is a
   supported trigger; the tag is the only thing that should).
4. Wait for the run to finish; download the archives + `SHA256SUMS.txt` + provenance.
5. Fill the `PENDING_CI_RUN_*` placeholders in `docs/release/0.1.0-readiness.md`,
   `docs/release/0.1.0-handoff.md` and `docs/notes/V0_1_CLOSURE_PLAN.md` with the real artifact
   names and hashes, and commit the update **before** announcing anything.
6. Publishing a GitHub Release is not implemented in the workflow (`contents: read`); if a
   Release page is wanted, upload the archives + `SHA256SUMS.txt` manually and state the license
   position and unsigned status in the description. **Do not publish publicly while
   `R-LICENSE` is open.**

## 9. Rollback instructions

- **Before publishing:** nothing is public. Delete the run's artifacts or simply abandon the
  candidate; no consumer is affected.
- **After a tag without a Release page:** `git push origin :refs/tags/v0.1.0` (delete the remote
  tag) and `git tag -d v0.1.0` locally, then remove the Actions artifacts. The workflow creates
  no Release and pushes no commits, so nothing else needs reverting.
- **After a manual Release page:** delete the Release first, then the tag/artifacts as above.
- **Candidate invalidation:** if a defect is found on the candidate SHA, prefer a new candidate
  (new commit + new run) over re-tagging; record the invalidation in
  `docs/release/risk-register.md` §candidate-invalidation instead of silently moving the tag.
- **Never** force-push `main` to undo a release commit; add a follow-up commit.
